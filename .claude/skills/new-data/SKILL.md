# new-data — слой данных фичи

Один вход на всё, что лежит между бэкендом/диском и блоком. Разработчик не должен помнить,
какой агент за что отвечает, — скилл выбирает исполнителя сам и сводит результат в один
репозиторий с одним контрактом.

## Как это устроено в проекте

```
/new-data  ──▶  api-integrator      сеть: модели, эндпоинты, Result
           ──▶  database-builder    хранение: таблицы, DAO, миграции, кэш
           ──▶  регистрация в DI + сигнатуры для блока
```

Скилл — точка входа разработчика. Агент — исполнитель в своём контексте. Экран и блок
этот скилл **не трогает**: он отдаёт готовые методы репозитория, а их вызов — работа
`screen-builder` или `/new-screen`.

## Аргументы

Свободное описание. Примеры:

```
/new-data подключи поиск альбомов: GET /search/album?q=
/new-data закэшируй избранное, чтобы открывалось офлайн
/new-data сохрани последние 20 поисковых запросов локально
```

## Шаг 1. Определить, что нужно

| Из запроса следует | Кто делает |
|---|---|
| только запрос к бэку | `api-integrator` |
| только локальное хранение | `database-builder` |
| данные с бэка, которые должны переживать перезапуск | оба, **по очереди**: сначала сеть, потом кэш поверх |
| один флаг или настройка | никто: это `AppPreferences` (`storage.md` §1), сделай сам, агент избыточен |
| данные нужны только на время сессии | никто: поле в репозитории, скажи об этом в отчёте |

Два агента параллельно не запускаются: `database-builder` встраивает кэш **в тот же**
репозиторий, который отдал `api-integrator`, и должен видеть его результат.

## Шаг 2. Уточнить недостающее

Одним блоком, до вызова агентов. Спрашивать только то, что не следует из запроса:

1. **Фича** — к какой предметной области относится (`lib/features/<feature>/`).
2. **Контракт бэка** — метод, путь, параметры, пример ответа. Примера нет — так и скажи:
   структура будет собрана по документации и потребует проверки на живом ответе.
3. **Ошибки** — умеет ли бэк отдавать ошибку кодом 200 в теле (тогда нужен `validateJson`).
4. **Пагинация** — есть ли, чем листается (страница/курсор).
5. **Хранение** — что должно переживать перезапуск и что чистится при разлогине.

Ответов нет — прими решения, явно перечисли допущения в отчёте.

## Шаг 3. Вызвать исполнителя

Передай агенту: фичу, контракт, ответы из шага 2 и требование не трогать блоки и UI.

- `api-integrator` — работает по `.claude/rules/network.md` и `models.md`;
- `database-builder` — по `.claude/rules/storage.md`, сначала проверяет, нужна ли БД
  вообще, и **останавливается**, если пакет БД не согласован.

## Шаг 4. Свести и зарегистрировать

После агентов проверь сам, глазами:

- у фичи **один** репозиторий, а не два (сетевой и «кэшевый»): выбор источника — его
  внутреннее дело (`storage.md` §3);
- сигнатуры публичных методов — `Future<Result<DomainType>>`, наружу не торчат ни dio,
  ни entity, ни `Map`;
- регистрация в `lib/di/di_core.dart`: репозиторий и `ApiService` — `registerLazySingleton`,
  каждый в `if (!sl.isRegistered<T>())` (`di.md`);
- `baseUrl` и таймауты приехали из флейвора и констант, а не литералами.

## Шаг 5. Проверить

```bash
dart run build_runner build --delete-conflicting-outputs
flutter analyze
```

`No issues found!` — обязательно. Затем `/check` по диффу.

## Отчёт

- что сделано и кем из агентов;
- **сигнатуры методов репозитория** — то, что блок будет вызывать, и что получит;
- как распознаётся ошибка бэка;
- стратегия кэша, если он есть, и что чистится при разлогине;
- что не проверено на живом ответе;
- что нужно сделать в блоке — списком, но **не делая этого**;
- принятые допущения.
