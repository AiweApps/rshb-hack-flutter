# new-feature — фича целиком

Фича — это вертикаль: данные → блок → экран → маршрут. Отдельные скиллы уже умеют делать
каждый слой; этот собирает их в правильном порядке и проверяет стык, на котором обычно
и ломается — сигнатуры репозитория против того, что вызывает блок.

**Когда не нужен:** если добавляется экран в существующую фичу — это `/new-screen`.
Если нужен только запрос или только хранение — `/new-data`. Не разгоняй вертикаль там,
где нужен один слой.

## Аргументы

```
/new-feature избранное: список сохранённых треков, добавление и удаление
/new-feature профиль пользователя с настройками уведомлений
```

## Шаг 1. Разобрать и уточнить

Вывести из запроса:

| Что | Пример |
|---|---|
| имя фичи (каталог) | `favorites` |
| экраны фичи | список + деталь, или один |
| источник данных | эндпоинт / локальное хранение / оба / ничего |
| точка входа | новая вкладка, экран внутри существующей вкладки, поверх всего |

Задать **одним блоком** то, что не следует из запроса:

1. откуда открывается первый экран фичи;
2. контракт бэка (метод, путь, пример ответа) — если данные приходят из сети;
3. что должно переживать перезапуск — если есть локальное хранение;
4. заголовки экранов на en и de;
5. какие действия есть у пользователя (добавить, удалить, обновить, поделиться).

Ответов нет — прими решения и явно перечисли допущения. Не выдумывай контракт бэка молча:
собранная по догадке модель отмечается в отчёте как непроверенная.

## Шаг 2. Порядок сборки

Строго по очереди — каждый следующий шаг опирается на результат предыдущего.

### 2.1. Слой данных — `/new-data`

Первым, потому что от сигнатур репозитория зависит блок. Если данных у фичи нет
(экран показывает то, что уже есть в приложении) — шаг пропускается.

### 2.2. Экран — `/new-screen`

Для каждого экрана фичи. Скилл сам заводит блок, стейт, ui-эффекты, четыре файла UI,
ключи локализации, регистрацию блока в DI и маршрут.

### 2.3. Наполнение — `screen-builder`

Если в запросе была вёрстка/макет. Каркас от `/new-screen` наполняется контентом,
данные берутся из стейта, действия шлются событиями.

## Шаг 3. Свести слои

Это то, ради чего скилл существует. Проверить руками после всех шагов:

- **блок вызывает ровно те методы**, которые отдал слой данных: имена, параметры,
  возвращаемые типы совпадают;
- в блоке разобраны **обе** ветки `Result`: `Success` и `Error`, у ошибки выставлен
  `errorType` (`errors.md`);
- у фичи один репозиторий, зарегистрированный `lazySingleton`; блоки — `factory`
  (`di.md`);
- маршруты добавлены в `Pages`, **включая `Pages.all`**, и в `AppRouterExtension` есть
  именованные методы перехода (`navigation.md`);
- ключи локализации есть в **обоих** ARB;
- если фича — новая вкладка, добавлен пункт в `CustomBottomNavigationBar`.

## Шаг 4. Проверить

```bash
dart run build_runner build --delete-conflicting-outputs
flutter gen-l10n
flutter analyze
```

`No issues found!`, затем `/check` по диффу. Дифф большой — прогоняй `/check` обязательно,
глазами такой объём не проверяется.

## Итоговая структура

```
lib/features/<feature>/
  application/bloc/     <screen>_bloc.dart, _event.dart, _state.dart, _uieffect.dart
  domain/
    models/             DTO и domain-модели
    <feature>_api_endpoints.dart
    <feature>_api_repository.dart
    dao/                если есть локальное хранение
  presentation/
    <screen>/           _page, _content, _loading, _error, components/
```

## Отчёт

- дерево созданных файлов;
- сигнатуры методов репозитория и какие события блока их дёргают;
- как открывается фича и каким методом `AppRouterExtension`;
- добавленные ключи локализации и токены;
- принятые допущения;
- что осталось: незаполненный контент, непроверенный контракт бэка, открытые вопросы
  по именам токенов.
