# Правила: DI и старт приложения

Контейнер — `get_it`, доступ — `sl` из `lib/shared/helpers/service_locator.dart`,
регистрация — `lib/di/di_core.dart`.

## Кому можно звать `sl<...>()`

| Слой | Можно | Почему |
|---|---|---|
| Блок | да | это его зависимости |
| Роутер (`app_router.dart`) | да | создаёт блоки для маршрутов |
| Другой сервис/репозиторий | да, в конструкторе или полем | |
| `di_core.dart` | да | |
| `presentation/**` | **нет** | `screens.md` §6 |
| `core/extensions/`, `core/helpers/` | **нет** | они должны быть чистыми и переиспользуемыми |
| Модели (`domain/models/`) | **нет** | модель — данные, а не поведение |

Зависимость резолвится **один раз полем класса**, а не по вызову `sl<X>()` в каждом методе:

```dart
// ✅
class HomePageBloc extends BaseBloc<HomeEvent, HomeState> {
  final MusicApiRepository _repository = sl<MusicApiRepository>();
```

## Чем регистрировать

| Тип | Что | Почему |
|---|---|---|
| `registerFactory` | **блоки** | новый экземпляр на каждое открытие экрана; старый умирает вместе с маршрутом |
| `registerLazySingleton` | репозитории, сервисы, `ApiService` | один экземпляр, создаётся при первом обращении |
| `registerSingleton` | то, что обязано существовать до `runApp` и требует `await` при создании | `AppPreferences`, `AppFlavorService`, `AppRouter` |

**Репозиторий — не `factory`.** `factory` создаёт новый объект на каждый `sl<>()`.
Пока репозиторий без состояния, это просто мусор в памяти; как только появится кэш,
дедупликация запросов или `CancelToken` на уровне репозитория — начнутся «необъяснимые»
баги: у каждого блока свой экземпляр.

**Блок — всегда `factory`.** Синглтон-блок переживает закрытие экрана и приносит на новый
экран старое состояние.

Долгоживущий блок (плеер, авторизация — то, что живёт дольше одного экрана) — осознанное
исключение: регистрируется `lazySingleton`, провайдится выше по дереву (не в билдере
маршрута) и **не** закрывается страницей. Такой блок заводится только по согласованию,
а не «потому что удобно».

## Как регистрировать

```dart
Future<void> _registerApiRepositories(GetIt sl) async {
  if (!sl.isRegistered<ApiService>()) {
    sl.registerLazySingleton<ApiService>(
      () => ApiService(sl<AppFlavorService>().apiBaseUrl, const {}),
    );
  }
  if (!sl.isRegistered<MusicApiRepository>()) {
    sl.registerLazySingleton<MusicApiRepository>(
      () => MusicApiRepository(sl<ApiService>()),
    );
  }
}
```

- `if (!sl.isRegistered<T>())` — обязательно вокруг **каждой** регистрации, включая
  создание вспомогательных объектов вроде `ApiService`: объект, созданный рядом с
  контейнером, а не в нём, невозможно подменить и легко продублировать;
- регистрируется **интерфейс/базовый тип, если он есть** (`AppFlavorService`), иначе
  конкретный класс;
- зависимости внутри фабрики резолвятся из `sl`, а не создаются рядом: иначе объект
  дублируется в обход контейнера.

## Ошибка инициализации фатальна

```dart
// ❌ приложение стартует с полупустым контейнером
} on Exception catch (error) {
  debugPrint(error.toString());
}
```

Приложение стартует с полупустым контейнером и падает позже, в случайном месте, с
непонятным `Object/factory with type X is not registered`. Настоящая причина к этому
моменту уже потеряна.

Правильно: ошибку инициализации **не глушить** — отправить в Crashlytics и пробросить
дальше, чтобы приложение падало сразу и честно. Показ экрана фатальной ошибки вместо
падения — допустимая альтернатива, но это осознанное решение, а не пустой `catch`.

## Порядок старта

Порядок в `main()` фиксирован:

1. `WidgetsFlutterBinding.ensureInitialized()`;
2. `initDependencies()` — контейнер;
3. Firebase (нужен флейвор из контейнера);
4. `LanguageService.initialize()`, `ThemeService.initialize()`;
5. `FlutterError.onError`;
6. `runApp`.

Правила:

- в `main()` нет прямых `SharedPreferences.getInstance()` и прочих обращений к платформе —
  всё это внутри `initDependencies`;
- всё, что требует `await` до первого кадра, регистрируется `registerSingleton` и
  проходит через `sl.allReady()`;
- всё остальное — ленивое. Каждый новый `await` в старте — это задержка сплэша;
- сервис — обычный класс в контейнере, а не статический синглтон с `initialize()`:
  статику нельзя подменить и нельзя проследить по зависимостям.

## Когда дробить `di_core.dart`

Сейчас всё в одном файле с тремя приватными функциями — это нормально. Дробить на
`di_<feature>.dart`, когда выполняется хотя бы одно:

- файл перевалил за ~150 строк;
- у фичи больше трёх своих регистраций;
- фича регистрирует свой `ApiService`/БД.

Тогда: `lib/di/di_core.dart` (ядро) + `lib/di/di_<feature>.dart`, и `initDependencies`
вызывает их по очереди. Единая точка входа остаётся одна.

## Чего не делать

- не звать `sl<>()` в `build()` виджета — ни разу, ни «только чтобы прочитать»;
- не регистрировать виджеты, стейты, модели;
- не делать глобальных статических синглтонов в обход контейнера (`static final instance`) —
  их нельзя подменить и нельзя проследить;
- не резолвить блок другого экрана, чтобы дёрнуть у него метод. Связь между блоками —
  через сервис/стрим (`bloc.md`);
- не регистрировать одно и то же под двумя типами.

## Чек-лист

- [ ] блоки — `registerFactory`, репозитории и сервисы — `registerLazySingleton`;
- [ ] каждая регистрация обёрнута в `if (!sl.isRegistered<T>())`;
- [ ] зависимости внутри фабрики берутся из `sl`, а не создаются заново;
- [ ] в `presentation/`, `extensions/`, `helpers/` нет `sl<`;
- [ ] `baseUrl` и прочая конфигурация приходят из флейвора, а не литералом (`flavors.md`);
- [ ] ошибка инициализации не проглочена.
