# Правила: общие виджеты, диалоги, боттом-шиты

## 1. Куда класть виджет

Три каталога, три разных ответа на вопрос «что этот виджет знает».

| Каталог | Что там | Знает о домене | Пример |
|---|---|---|---|
| `lib/core/widgets/` | виджеты без домена: кнопки, поля, диалоги, разделители, шиммеры, нижняя навигация | **нет** | `base_dialog.dart`, `custom_bottom_navigation_bar.dart` |
| `lib/shared/presentation/` | виджеты, знающие о понятиях приложения, но нужные нескольким фичам | да | `app_error_widget.dart` (знает `ErrorType`) |
| `features/<f>/presentation/<screen>/components/` | часть контента одного экрана | да | `track_card.dart` |

`lib/core/presentation/` — **не место для виджетов**. Там только тема (`base_theme.dart`)
и реестр ассетов (`app_icons.dart`).

Решающий вопрос при выборе: **что придётся импортировать, чтобы виджет собрался.**
Импорт из `features/**` или из `shared/` → виджет не может лежать в `core/`.

### Когда виджет переезжает

- компонент экрана понадобился на втором экране той же фичи → в
  `features/<f>/presentation/components/` (уровнем выше);
- понадобился в другой фиче → в `shared/presentation/`;
- из него ушли все доменные типы → в `core/widgets/`.

Переезд делается в момент второго использования, не «когда-нибудь». Копипаста виджета
в две фичи — нарушение.

## 2. Требования к общему виджету

- **`const`-конструктор**, если нет изменяемого состояния. Без него виджет перестраивается
  всегда (`performance.md`);
- **не знает о блоке.** Ни `context.read<XBloc>()`, ни `BlocBuilder`. Данные — через
  конструктор, действия — через колбэк (`VoidCallback onTap`, `ValueChanged<T> onChanged`).
  Это то же правило, что для `components/` в `screens.md` §5, и оно тем более строго для
  `core/` и `shared/`;
- **не ходит в `sl<>()`, не грузит данные, не навигирует** — ничего из `screens.md` §6;
- **не знает про фичи**: в `lib/core/**` нет импортов из `lib/features/**`;
- параметры-колбэки называются `onX` и ничего не возвращают, кроме случая
  `ValueChanged`/`bool Function()`;
- цвета, стили, размеры — только токены (`theme.md`, `constants.md`). Общий виджет с
  захардкоженным цветом ломает тему во всех фичах сразу;
- у виджета есть doc-комментарий `///`, если из имени не очевидно, чем он отличается от
  соседнего (`base_dialog` vs `confirmation_dialog`).

## 3. Диалоги и боттом-шиты

### Кто их показывает

Показ диалога — **сайд-эффект**. По `screens.md` §6 в `presentation/` сайд-эффектов нет,
кроме `_onUiEffect`. Значит:

```
UI ──add(DeleteTapped)──▶ Bloc ──emitUiEffect(ConfirmDelete)──▶ _onUiEffect на странице
                                                                    показывает диалог
                                                                          │
                            Bloc ◀──add(DeleteConfirmed)──────────────────┘
```

```dart
// ❌ в content/компоненте
onTap: () async {
  final ok = await showDialog<bool>(...);
  if (ok == true) context.read<Bloc>().add(...);
}

// ✅ в content/компоненте
onTap: () => context.read<Bloc>().add(const DeleteTapped()),

// ✅ на странице, в _onUiEffect
case ConfirmDelete(:final itemTitle):
  final confirmed = await ConfirmationDialog.show(context, title: itemTitle);
  if (!context.mounted) return;
  if (confirmed) context.read<Bloc>().add(const DeleteConfirmed());
```

Так решение «спрашивать ли подтверждение» остаётся в блоке: его можно отключить настройкой,
залогировать и протестировать, не поднимая виджеты.

### Требования

- `await` после показа — проверка `context.mounted` перед использованием контекста;
- результат диалога **всегда** уходит событием в блок, а не выполняется на месте;
- отмена (тап мимо, свайп вниз, «назад») — тоже результат: обрабатывается явно,
  `null` не игнорируется молча;
- тексты — из ARB, включая кнопки (`localization.md`);
- каждый диалог/шит показывается через статический `show`-метод своего класса, а не
  голым `showDialog(builder: ...)` на месте вызова — иначе оформление расползётся;
- боттом-шит с полями ввода — `isScrollControlled: true` и учёт клавиатуры
  (`adaptive.md`), см. lib/core/widgets/dialog/base_bottom_sheet.dart:10;
- вложенных диалогов не бывает: новый показывается после закрытия предыдущего.

### Что уже есть

Перед новым диалогом — посмотреть `lib/core/widgets/dialog/`: `base_dialog`,
`base_bottom_sheet`, `confirmation_dialog`, `picker_dialog`, `dialog_success_step`,
`dialog_error_step`, `dialog_result_step`. Новый диалог собирается **из** них, а не рядом
с ними.

Так же и с остальным содержимым `lib/core/widgets/`: например, любая картинка из сети —
это `RemoteImage` (`presentation.md`), а не собственный `Image.network` с плейсхолдером.

## 4. Тосты

Тост — уже готовый ui-эффект: `emitSnackBar.info/success/error` в блоке
(lib/core/application/bloc/base_bloc.dart:24), перехватывается
`BaseBlocPresentationListener` сам. Отдельный эффект под тост не заводится,
`ScaffoldMessenger` в фиче не вызывается.

Текст тоста — из ARB, через `lsl10n` в блоке (`localization.md`, `errors.md`).

## 5. Состояния общих виджетов

Общий интерактивный виджет обязан выглядеть осмысленно во всех состояниях: обычное,
нажатое, `disabled`, загрузка, длинный текст, пустое значение. `disabled` — отдельный
параметр (`onTap == null`), а не «просто не реагирует».

Списки и карточки, которые могут ждать данных, получают шиммер/скелетон в том же
каталоге, а не собираются из `CircularProgressIndicator` на каждом экране заново.

## Чек-лист

- [ ] виджет лежит там, где ему позволяют его импорты;
- [ ] `const`-конструктор, если нет состояния;
- [ ] нет обращений к блоку, `sl<>()`, навигации, `await`;
- [ ] цвета/стили/размеры — токены, ни одного литерала;
- [ ] диалог показывается из `_onUiEffect`, результат уходит событием;
- [ ] после `await` проверен `context.mounted`;
- [ ] тексты в ARB;
- [ ] похожего виджета ещё нет в `core/widgets/` и `shared/presentation/`.
