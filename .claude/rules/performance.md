# Правила: производительность

Правило не про микрооптимизации, а про несколько вещей, которые в этом проекте
гарантированно всплывут: списки, картинки из сети, объём перерисовки и работа на UI-потоке.

## 1. Списки

- список неизвестной длины — **только** `ListView.builder` / `GridView.builder`.
  `ListView(children: [...])` строит все элементы сразу и лагает уже на сотне карточек;
- у элемента списка обязателен `const`-конструктор, если он не зависит от изменяемого
  состояния;
- `shrinkWrap: true` + вложенный скролл — крайняя мера: он строит **весь** список.
  Вместо этого `CustomScrollView` + `SliverList`;
- при пагинации не пересоздавать список целиком: новая страница добавляется к
  существующему списку в стейте (`bloc.md`);
- `Key` у элементов — если элементы переупорядочиваются или удаляются, иначе состояние
  прилипает не к тем карточкам.

## 2. Картинки из сети

Картинка из сети рисуется только через `RemoteImage` (`presentation.md`). Он уже даёт
дисковый кэш и ограничивает размер декодирования — голый `Image.network` в списке
перезагружает картинку при каждом прокруте и держит в памяти полноразмерный оригинал.

От вызывающего кода требуется одно: **всегда задавать `width` и `height`**. Из них
считается размер декодирования, и по ним раскладка не дёргается, когда картинка приедет.

## 3. Область перерисовки

- `BlocBuilder` ставится **как можно ниже** по дереву. Билдер на весь экран
  перестраивает всё, включая неизменные части;
- часть экрана зависит от одного поля стейта → `BlocSelector` или `buildWhen`;
- `const` у виджетов — самый дешёвый способ убрать лишние перестроения. Виджет без
  изменяемых параметров обязан быть `const`;
- тяжёлое поддерево, которое не зависит от перестройки, передаётся в `child:`
  билдера или `ValueListenableBuilder` — оно строится один раз;
- анимации — `AnimatedBuilder` с `child:`, а не пересборка поддерева на каждый кадр;
- `RepaintBoundary` — только по факту замера, а не «на всякий случай».

## 4. Работа вне UI-потока

- в `build()` нет вычислений: ни сортировки, ни фильтрации, ни парсинга. По `screens.md` §6
  это и так запрещено — здесь та же причина с другой стороны: `build` зовётся на каждый кадр
  анимации;
- парсинг большого JSON, обработка изображений, массовая вставка в БД — `compute()` /
  `Isolate`. Ориентир: операция дольше ~16 мс на UI-потоке — это пропущенный кадр;
- `json.decode` ответа идёт на UI-потоке: для обычных ответов это нормально, для списков
  в тысячи элементов разбор выносится в `compute()`.

## 5. Память и утечки

- всё заведённое освобождается: контроллеры в `dispose()` виджета, подписки и таймеры в
  `close()` блока (`bloc.md`);
- блок регистрируется `factory` и умирает вместе с маршрутом (`di.md`) — синглтон-блок
  держит стейт и подписки на всё время жизни приложения;
- listener, добавленный руками (`addListener`), снимается тем же кодом, который его добавил.

## 6. Старт приложения

- каждый `await` в `main()` до `runApp` — задержка первого кадра (`di.md`);
- всё, что не нужно до первого экрана, регистрируется лениво;
- сплэш не должен ждать данных, которые нужны не сразу.

## Когда оптимизировать

Не раньше, чем есть проблема, которую видно: пропущенные кадры в профайлере, заметный
лаг при скролле, разогрев устройства. Правила выше — не оптимизация, а нормальное письмо:
они ничего не усложняют.

```bash
flutter run --profile --flavor dev -t lib/main.dart
```

Замер — в profile-сборке. В debug производительность нерепрезентативна, и выводы по ней
неверны.

## Чек-лист

- [ ] длинные списки — через `.builder`;
- [ ] картинки из сети — через общую обёртку с кэшем и плейсхолдером;
- [ ] размеры контейнера картинки известны до загрузки;
- [ ] `BlocBuilder` не оборачивает больше, чем нужно;
- [ ] виджеты без изменяемых параметров — `const`;
- [ ] в `build()` нет вычислений;
- [ ] контроллеры, подписки, таймеры освобождаются.
