# Правила: локальные данные, кэш, база

Правило описывает всё, что приложение хранит на устройстве. Тонкие обёртки над платформой
остаются в `misc/` (`misc.md`), здесь — что где хранить, как это попадает в приложение
и кто про это знает.

## 1. Выбор хранилища

| Что храним | Куда | Почему не иначе |
|---|---|---|
| Флаги, выбор языка/темы, «онбординг пройден», мелкие настройки | `SharedPreferences` через `AppPreferences` | быстро, синхронное чтение после инициализации |
| Токены, пароли, ключи, персональные идентификаторы | **secure storage** | prefs — обычный файл, читается на рутованном устройстве и попадает в бэкапы |
| Списки сущностей, офлайн-данные, история, кэш ответов | **база** | prefs не умеют в запросы, сортировку и объём |
| Картинки, файлы, экспорт | файловая система + кэш-каталог ОС | |

Жёстко:

- **токен в `SharedPreferences` — запрещено**;
- **JSON-массив, сериализованный в строку prefs, — запрещено.** Это признак того, что
  нужна база (или что данные вообще не надо хранить);
- прямой `SharedPreferences.getInstance()` вне `AppPreferences` — запрещено (`misc.md`).
  Это касается и сервисов ядра: тема и язык читают свои значения через `AppPreferences`.

### `AppPreferences`

Каждое осмысленное значение — **именованная типизированная пара** геттер/сеттер
(`bool get isFirstLaunch` / `Future<void> setIsFirstLaunch(bool)`). Ключ — приватная
`const` в этом же файле.

Общие `getString`/`setString`/`getBool` — escape hatch для чужого кода, **не** способ
завести новый флаг. Новый флаг со строковым ключом на месте вызова — нарушение.

## 2. Слои базы

```
Entity / DAO            — схема и запросы. Знает про БД, не знает про сеть и UI.
      ↓
<Feature>Repository     — решает: сеть, кэш или оба. Отдаёт Result<DomainModel>.
      ↓
Bloc                    — просит данные, не зная откуда они.
```

Границы:

- **entity ≠ domain-модель.** Схема таблицы меняется по своим причинам (индексы,
  миграции, денормализация), домен — по своим. Маппинг `entity ↔ domain` лежит рядом
  с entity (`models.md`);
- **DAO не вызывается из блока и тем более из `presentation/`.** Только из репозитория;
- сетевой репозиторий и БД **не знают друг о друге**: их соединяет репозиторий фичи;
- у метода репозитория один и тот же контракт независимо от источника: `Future<Result<T>>`
  (`network.md`). Блок не должен различать «пришло из кэша» и «пришло из сети», кроме
  случаев, когда это осознанно показывается в UI («данные могут быть неактуальны»).

## 3. Единый источник правды

Решение «сеть или кэш» принимает **репозиторий**, не блок и не UI.

Стратегия выбирается явно и записывается в doc-комментарии метода:

| Стратегия | Когда | Поведение |
|---|---|---|
| `network-only` | данные обязаны быть свежими (оплата, баланс) | кэш не используется |
| `cache-then-network` | списки, ленты, каталог | сразу отдать кэш, затем обновить |
| `cache-first` (TTL) | справочники, редко меняющееся | сеть только если кэш просрочен |
| `network-then-cache` | нужна свежесть, но офлайн допустим | сеть, при ошибке — кэш |

`cache-then-network` отдаёт данные **дважды** — значит метод возвращает `Stream<Result<T>>`,
а не `Future`, либо репозиторий пишет в БД, а блок подписан на неё. Смешивать не надо:
на фичу выбирается один подход и держится.

Правила свежести:

- у кэшированной записи есть отметка времени; TTL — константа в `ApiConstants`,
  не литерал;
- «показываем устаревшее» — осознанное решение, а не побочный эффект: если данные из
  кэша могут быть старыми и это важно пользователю, это видно в UI;
- инвалидация описывается там же, где стратегия: что и когда чистится.

## 4. Разлогин и чистка

Одно место (`SessionCleaner`-подобный сервис), которое при разлогине:

- удаляет токены из secure storage;
- чистит пользовательские таблицы БД;
- сбрасывает пользовательские ключи prefs, **не трогая** настройки устройства (язык, тема);
- чистит кэш картинок и файлов, если он персональный.

Каждая новая таблица и каждый новый ключ обязаны быть учтены здесь **в тот же момент**,
когда заводятся. Забытая таблица — это данные предыдущего пользователя на экране
следующего.

## 5. Миграции

- у схемы есть версия; изменение схемы = новая версия + миграция. Без исключений;
- миграция не теряет пользовательские данные молча. Если данные не переносятся —
  это отдельное осознанное решение, а не «упростим»;
- удаление/переименование колонки — миграция, а не правка описания таблицы;
- провал миграции логируется в Crashlytics (`errors.md`), а не проглатывается;
- «уронить и создать заново» допустимо **только** для чисто кэшевых таблиц, и это
  пишется в комментарии к миграции.

## 6. Производительность и потоки

- любое обращение к БД асинхронно;
- тяжёлые операции (массовая вставка, парсинг большого ответа) — батчами/в транзакции,
  при заметном объёме — в `Isolate` (`performance.md`);
- запрос в цикле — запрещено: один запрос с `IN`/`join`;
- в БД не хранятся файлы и картинки — только пути к ним.

## 7. Секреты и приватность

- ключи и токены не логируются (`network.md`);
- персональные данные не кладутся в аналитику (`analytics.md`);
- на Android для prefs с чувствительными флагами учитывается автобэкап
  (`allowBackup`) — решается при появлении таких данных.

## 8. Выбор пакета БД

Пакет БД не добавляется без согласования (`CLAUDE.md` §3). Вопрос задаётся разработчику
с этими вариантами:

| Пакет | Плюсы | Минусы |
|---|---|---|
| `drift` (рекомендуемый) | типобезопасные запросы, миграции, `Stream` из коробки, кодогенерация в стиле проекта | больше кода, свой build_runner-шаг |
| `sqflite` | минимум магии, полный контроль SQL | руками: маппинг, миграции, типы |
| `isar` / `hive` | быстро на старте | слабее по запросам и миграциям, вопросы к поддержке |

`drift` рекомендуется потому, что проект уже живёт на кодогенерации (`freezed`,
`json_serializable`), а его `Stream`-запросы напрямую ложатся на `cache-then-network`.

Структура после подключения:

```
lib/core/database/
  app_database.dart          # объявление БД, версия, миграции
  tables/<name>_table.dart
lib/features/<feature>/domain/
  dao/<feature>_dao.dart
  models/<entity>.dart
```

`AppDatabase` регистрируется в DI как `lazySingleton`, DAO — тоже (`di.md`).

## Чек-лист

- [ ] токены — в secure storage, не в prefs;
- [ ] новый флаг — именованная пара в `AppPreferences`, ключ приватной константой;
- [ ] `SharedPreferences.getInstance()` не вызывается вне `AppPreferences`;
- [ ] entity не протекает в блок и UI, маппинг лежит рядом с entity;
- [ ] DAO зовётся только из репозитория;
- [ ] стратегия кэша выбрана явно и записана в doc-комментарии;
- [ ] TTL и лимиты — константы;
- [ ] новая таблица/ключ учтены в чистке при разлогине;
- [ ] изменение схемы сопровождается миграцией;
- [ ] пакет БД согласован с разработчиком.
