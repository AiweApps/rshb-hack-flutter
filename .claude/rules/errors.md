# Правила: ошибки

## Главное правило

**Пользователь никогда не видит техническую строку.** Ни текста исключения, ни имени
класса, ни `DioExceptionType`, ни ответа бэка «as is». Всё, что показывается человеку, —
ключ из ARB (`localization.md`).

Техническая информация нужна разработчику, а не пользователю: её место — Crashlytics и лог,
а не тост.

## Путь ошибки

```
dio / парсер
   ↓  handleAPICall
AppError            — техническая причина: ApiError | ParsingError | DefaultError | StringError
   ↓  блок
ErrorType           — что показать: connection | server
   ↓  стейт (screenStatus: error, errorType: ...)  или  ui-эффект (тост)
UI                  — AppErrorWidget / SnackBar с текстом из ARB
```

Каждая стрелка — обязательный переход. `AppError` **не доходит до UI никогда**.

## Классификация: `AppError` → `ErrorType`

Маппинг — один на весь проект, а не по копии в каждом блоке.

Место: `lib/shared/presentation/errors/error_type.dart`, extension на `AppError`:

```dart
extension AppErrorType on AppError {
  ErrorType get asErrorType => switch (this) {
    ApiError(:final exceptionType) when exceptionType.isConnectionIssue =>
      ErrorType.connection,
    _ => ErrorType.server,
  };
}
```

К `connection` относятся: `connectionTimeout`, `sendTimeout`, `receiveTimeout`,
`connectionError`, `SocketException`. Всё остальное — `server`.

`DioExceptionType.cancel` — **не ошибка**. Отменённый запрос не показывается пользователю
вообще (см. `network.md`).

## Выбор канала: экран, блок или тост

Решает блок, и решает по одному признаку — **есть ли что показать без этих данных**.

| Ситуация | Как показать | Что в стейте |
|---|---|---|
| Первичная загрузка провалилась, контента нет | полноэкранная ошибка | `screenStatus: error`, `errorType` |
| Провалилась часть экрана (одна секция из трёх) | ошибка блоком внутри контента | `screenStatus: content` + поле секции |
| Провалилось действие поверх готового контента (обновление, лайк, отправка) | тост | `screenStatus: content` |
| Догрузка следующей страницы | тост или строка в конце списка, список остаётся | `screenStatus: content` |

`AppErrorWidget` уже умеет оба варианта — `ErrorDisplay.fullScreen` и блок. Свою вёрстку
ошибки не писать.

### Ошибку нельзя проглатывать

Провалившийся запрос обязан привести хоть к чему-то видимому: экрану, блоку или тосту.
Молча вернуть `content` с пустым списком — запрещено: пользователь решит, что данных нет,
и не нажмёт «повторить».

Отсюда следствие: если экран умеет показывать ошибку, в его стейте **есть** поле
`errorType`. Стейт без него не оставляет блоку выбора канала — только тост.

## Тексты

- Тексты `ErrorType` уже заведены и локализованы — `errorConnectionTitle`,
  `errorServerTitle`, `errorConnectionSubtitle`, `errorConnectionFullScreenTitle`,
  `errorServerSubtitle`. Новые сообщения — туда же, в ARB.
- Сообщение из тела ответа бэка показывается пользователю, **только** если бэк гарантирует,
  что оно предназначено для человека и локализовано. По умолчанию — не показывается:
  оно уходит в лог, а пользователю показывается ключ из ARB.
- `error.getErrorMessage()` — **отладочный** метод. Его результат идёт в лог и в
  Crashlytics, не в UI. В `emitSnackBar.error(...)` он не попадает никогда.

### `emitErrorSnackBar`

`emitErrorSnackBar(error)` в `BaseBloc` — единственный правильный способ показать ошибку
тостом из блока. Его контракт:

- текст берётся из ARB по `error.asErrorType` через `lsl10n` (в блоке нет контекста —
  `localization.md`);
- техническая причина в тот же момент уходит в лог и, если она того заслуживает
  (см. таблицу ниже), в Crashlytics.

Собирать текст тоста из полей `AppError` на стороне блока не нужно — это дублирование
того, что уже делает база.

## Что логировать, а что нет

| Ошибка | Пользователю | Crashlytics |
|---|---|---|
| Нет сети, таймаут | ошибка/тост | нет — это не баг приложения |
| 5xx от бэка | ошибка/тост | да, non-fatal |
| 4xx (кроме 401/403) | ошибка/тост | да, non-fatal — обычно это баг клиента |
| 401/403 | обычно ничего: рефреш или разлогин | да, если рефреш не сработал |
| `ParsingError` | общая ошибка сервера | **да, обязательно** — это расхождение контракта |
| Отменённый запрос | ничего | нет |
| `RenderFlex overflowed`, падение загрузки картинки | ничего | нет (`FirebaseExceptionHandler`) |

`ParsingError` — самый важный пункт: это единственный сигнал о том, что бэк поменял
контракт. Он обязан долетать до Crashlytics с `keyPath` и именем модели.

## Необработанные исключения

`runZonedGuarded` + `FlutterError.onError` в `main()` — единственная точка сбора.

- классификация «что нефатально» — в `FirebaseExceptionHandler` (`misc.md`), а не
  условиями внутри `main.dart`;
- обработчик обязан отправлять ошибку в Crashlytics, а не только печатать её в debug;
- падение инициализации приложения (DI, флейвор) — фатально и должно быть видно,
  а не проглочено (`di.md`).

## Ошибки в UI-слое

- В `presentation/` нет `try/catch` — ловить там нечего, логики нет.
- Виджет не решает, что показать при ошибке: он рисует то, что уже посчитал блок
  (`state.errorType`).
- `?? ''`, `?? 0`, `!` на данных из сети — это молчаливое проглатывание. Значение по
  умолчанию задаётся в модели (`models.md`), а не в вёрстке.

## Чек-лист

- [ ] пользователь видит только текст из ARB;
- [ ] `AppError` не пересекает границу `presentation/`;
- [ ] в стейте есть `errorType`, если экран умеет показывать ошибку;
- [ ] канал (экран / блок / тост) выбран по наличию контента;
- [ ] отменённый запрос не показывается как ошибка;
- [ ] `ParsingError` уходит в Crashlytics;
- [ ] у полноэкранной ошибки есть работающий `onRefresh`.
